des couches, des interfaces, des tests

Un banc de test, c'est d'abord du logiciel fiable. Le kit banclaser est organisé en couches qui ne se parlent qu'à travers des interfaces : c'est ce qui permet de tout tester sur ton PC avec un banc simulé, puis de passer au vrai matériel sans changer une ligne.

à la fin de cette page, tu sauras…

  • expliquer l'organisation du code en couches et le rôle de chaque dossier ;
  • comprendre l'injection de dépendances et le banc simulé ;
  • appliquer les règles de sécurité dans le code ;
  • travailler en « tests d'abord » avec pytest ;
  • enregistrer des données traçables.

2l'injection de dépendances

Ton pilote ADS1115 ne crée pas son bus I²C : il le reçoit dans son constructeur. Sur la Pi on lui passe un BusI2CSmbus, dans les tests un FauxBusI2C qui imite le composant au niveau des octets. Même chose pour l'horloge : en simulation, horloge.dormir(0.1) fait avancer un temps virtuel instantanément — un essai de régulation de 5 minutes s'exécute en une fraction de seconde.

from banclaser.simulation import creer_banc_simule
from banclaser.instruments.ads1115 import ADS1115

banc = creer_banc_simule()                       # sur la Pi : BusI2CSmbus(1), HorlogeReelle()
adc = ADS1115(banc.bus, 0x49, gamme=4.096, cadence=128, horloge=banc.horloge)
print(adc.lire_tension(1))                       # ≈ 2,5 V (alimentation du driver / 2)

3la sécurité dans le code

  • Défaut sûr : à la création d'un objet, rien ne s'allume ; le relais reste fermé.
  • Vérifier avant d'agir : interlock, limites, état actif — et lever une exception explicite (InterlockOuvert, ErreurSecurite, ValueError) plutôt que d'ignorer.
  • Toujours remettre en sécurité : try … finally: driver.desactiver() autour de toute séquence ; desactiver() ne lève jamais d'exception.
  • Pas de valeur magique : limites, adresses et gains viennent de config/banc.toml.
  • Le matériel décide en dernier : le logiciel s'ajoute aux protections matérielles, il ne les remplace pas.

4« tests d'abord »

Chaque fichier à compléter a ses tests dans tests/. La boucle de travail :

  1. lire le test (il dit précisément ce qui est attendu) ;
  2. écrire le code le plus simple qui le fait passer ;
  3. pytest tests/test_01_ads1115.py ; lire le message d'erreur jusqu'au bout ;
  4. une fois vert : relire, nettoyer, commenter, git commit.

lire un échec pytest

pytest affiche la ligne du test qui échoue, la valeur obtenue et la valeur attendue (« Obtained / Expected »). Commence toujours par là : la plupart du temps, l'écart te dit directement où est l'erreur (unité, signe, décalage de bits…).

5des données traçables

  • Données brutes en CSV (séparateur « ; », point décimal), avec un en-tête de commentaires : date ISO, diode et n° de série, température, configuration, version du code (git describe), instrument de référence.
  • Un dossier par campagne : mesures/2026-12-03_diode-A/ avec CSV, figures PNG et rapport.
  • Journalisation avec le module logging : chaque action importante (activation, consigne, alarme) est horodatée dans un fichier.
  • On ne modifie jamais un fichier brut : on le relit et on calcule.

6style et outils

  • Noms en français explicites, une fonction = une tâche, docstrings, annotations de type.
  • numpy pour les calculs, matplotlib pour les figures, scipy pour le traitement du signal.
  • git : petits commits fréquents avec des messages clairs ; une branche par fonctionnalité si tu veux expérimenter.

à retenir

  • Couches : interface → mesures/analyse → instruments → interfaces matérielles → Pi ou simulateur.
  • Injection de dépendances : on passe bus, GPIO et horloge aux constructeurs.
  • Défaut sûr, vérifications, try/finally, configuration externe.
  • Tests d'abord ; données brutes CSV horodatées et traçables.

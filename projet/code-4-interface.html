code 4 · interface & rapport

une commande, une mesure, un rapport

Dernière couche : une interface en ligne de commande qui assemble pilotes, séquences et analyses, un chien de garde logiciel, un journal horodaté, et un rapport automatique qui compare les résultats au cahier des charges. C'est ce qui transforme un tas de fonctions en un banc qu'un collègue peut utiliser.

à la fin de cette page, tu sauras…

  • écrire les commandes etat, liv et temperature de cli.py, puis en ajouter ;
  • garantir l'arrêt sûr du laser, y compris sur Ctrl+C ou si le programme se fige ;
  • journaliser ce que fait le banc ;
  • générer un rapport HTML autonome qui conclut « conforme / non conforme » ;
  • choisir, si tu le veux, une interface graphique sans compromettre la sécurité.

1la ligne de commande

L'analyse des arguments est déjà écrite dans cli.py (module argparse) et la fonction construire_banc assemble tes pilotes sur le vrai matériel ou sur la simulation. Il te reste à écrire ce que fait chaque commande. Objectif : qu'une session ressemble à ceci.

banclaser --simule etat
# monture 25,00 °C · laser inactif · interlock fermé · I = 0,00 mA · P = 0,000 mW

banclaser --simule liv --fin 40 --pas 0.5
# [10:42:01] monture stabilisée à 25,00 °C
# [10:42:01] laser activé
# [10:42:09] 81 points mesurés — retour à 0 mA, laser désactivé
# seuil (régression)   20,0 mA     pente   0,63 mW/mA     R² 0,9998
# η externe            0,33        R série 6,2 Ω
# → mesures/2026-12-03_simule/liv_25C.csv  et  liv_25C.png

banclaser --simule temperature 20
# 25,00 → 20,00 °C : stable (±0,1 °C pendant 10 s) après 142 s ; Ctrl+C pour arrêter

Les codes de retour comptent : return 0 si tout va bien, autre chose sinon (utile si un script enchaîne plusieurs commandes).

Ajoute ensuite tes propres sous-commandes sur le même modèle : per, caustique, lambda-t, bruit, rapport. Chaque sous-commande = une fonction courte qui appelle les couches du dessous ; aucun calcul dans cli.py.

2s'arrêter proprement, toujours

  • Ctrl+C lève KeyboardInterrupt : les finally s'exécutent, le laser s'éteint. Vérifie-le à chaque nouvelle commande.
  • Arrêt du système ou kill : Python reçoit le signal SIGTERM, qui par défaut tue le programme sans exécuter les finally. Installe un gestionnaire (signal.signal(signal.SIGTERM, …)) qui lève une exception (par exemple SystemExit) : on retombe dans le cas précédent.
  • Programme figé (boucle infinie, bus I²C bloqué) : aucun finally ne s'exécutera. C'est le rôle du chien de garde matériel.
  • Panne de courant, plantage de la Pi : le relais normalement fermé court-circuite la diode et l'EEPROM du DAC redémarre à 0. Le logiciel n'y peut rien : c'est pour cela que la sécurité est d'abord matérielle.

le chien de garde

Le monostable 74HC123 du schéma du banc garde le relais alimenté tant qu'il reçoit une impulsion sur GPIO 27 au moins toutes les ~0,3 s. Piège classique : un fil d'exécution (thread) qui envoie des impulsions en boucle, quoi qu'il arrive… continue de les envoyer même quand le programme principal est figé. Le chien ne sert alors à rien.

indice — un chien de garde honnête
classe ChienDeGarde(sortie, horloge, periode=0.1, delai_max=0.2) :
    signer()  : derniere_signature ← maintenant          # appelé par les boucles de mesure
    boucle du fil :
        tant que actif :
            si maintenant − derniere_signature < delai_max :
                impulsion courte sur la sortie
            dormir(periode)

Les boucles longues (rampe, stabilisation, balayages) appellent signer() à chaque tour. Teste-le : un while True: pass volontaire doit faire retomber le relais.

3le journal de bord du programme

Le module logging horodate chaque événement et l'écrit à la fois à l'écran et dans journal.log du dossier de la campagne. Niveaux : DEBUG (trames, détails), INFO (étapes), WARNING (anomalie tolérée : température lente à se stabiliser), ERROR (mesure abandonnée), CRITICAL (sécurité : interlock).

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s %(name)s : %(message)s",
    handlers=[logging.FileHandler(dossier / "journal.log", encoding="utf-8"),
              logging.StreamHandler()],
)
log = logging.getLogger("banclaser.liv")    # un nom par module
log.info("laser activé, consigne %.2f mA", 0.0)

Ce qui doit apparaître : démarrage (version du code, configuration), chaque activation/désactivation du laser, chaque consigne, chaque alarme, la fin de chaque séquence avec le nom des fichiers écrits. En cas d'incident, c'est la première chose que tu liras.

4le rapport automatique

Un rapport de test est un document qualité : il identifie le composant testé, les conditions, les moyens de mesure (et leur étalonnage), les résultats avec incertitudes, et conclut par rapport à une spécification. Génère-le en HTML (un seul fichier, figures incluses en base64 : il s'envoie par mail et s'ouvre partout).

  • Gabarit : une chaîne HTML avec des champs à remplir (string.Template ou une f-string) ; le style tient dans une balise <style>.
  • Figures : PNG lus en binaire, encodés avec base64.b64encode, insérés en <img src="data:image/png;base64,…">.
  • Spécifications : dans un fichier (par exemple config/specification_diode.toml), jamais dans le code.
  • Traçabilité : la commande rapport relit les CSV d'une campagne ; elle ne remesure rien. Un rapport doit pouvoir être régénéré à l'identique.

25,2 mA dépasse la limite alors que la mesure elle-même est dessous : l'intervalle chevauche la spécification → indéterminé. Il faut réduire l'incertitude (plus de mesures, meilleur étalonnage) avant de conclure.
